# 参考图场景重建方案

状态：用户已批准并实施海岸资产重建。本文保留原始目标；实际完成范围、验证结果和剩余差距见 [交付记录](coast-rebuild-2026-09-08.md)。

范围：海岸场景的模型、布局、材质、灯光与渲染性能。玩法、AI、代币系统及角色车辆模型继续由对应任务负责。

## 判断

目标是参考图所示的风格化写实：树冠和岩石具有经过设计的棱面，建筑边缘有细小倒角，材质的粗糙度和表面起伏可辨，阳光下的明暗具有间接光照层次。

当前版本已经有 PBR 材质、环境反射和动态阴影，但场景主体仍是基础几何体组合与规则化布置。`public/content.json` 的 `sceneModel` 仍为空；项目中的 GLTFLoader 入口目前是追加场景，不能直接承担分区替换、材质烘焙数据绑定与距离分级。仅换文件格式、增加多边形或继续调整曝光，均不能保证美术质量提升。

参考图不是完整三维资料。两张图可以约束可见轮廓、布局、材质和灯光观感；看不到的结构需要补充设计，也不能唯一恢复原始网格、相机、灯光参数。验收应按可见目标逐项比较，不能凭主观宣称“还原度 95%”。

## 路线选择

| 路线 | 成本与效果 | 决策 |
| --- | --- | --- |
| 精修可复用资产，烘焙静态间接光照，接入现有实时渲染器 | 需要建立资产流程，能够同时改善模型、材质、光影及维护方式 | 推荐 |
| 继续在现有几何体上叠加细节和后处理 | 接入较快，但原有比例、轮廓和布局问题仍需独立解决 | 仅用于辅助细节 |
| 重建到其他游戏引擎 | 需要重新集成游戏与网络系统，不能自动产生参考级资产 | 不纳入当前场景任务 |

## 实施顺序与验收关口

### 1. 建立参考拆解和镜头基准

记录两张图片的画幅、地平线、道路消失方向、房屋与树冠轮廓、灯塔位置、护栏高度，以及投影方向。将车辆作为比例参照，保持车辆资源不变。

先制作约 150–200 米的海岸美术样板段，包含近景路肩、中景村落、远景灯塔和海面。样板使用真实运行时资产，可切换前视、后视及自由检查相机；同时显示未加纹理的模型，先排除比例和构图问题。

正式路线的弯向若与参考构图冲突，记录冲突并交由道路任务对齐。场景不得通过单独挪动可见路面造成画面与碰撞错位。独立样板的画面不作为正式赛道已完成的证据。

通过条件：两个参考角度均有逐项轮廓和布局对照；不存在近景树冠过大、房屋排成整齐墙面、草地形成大块空白、灯塔出现在错误景深层级的问题。

### 2. 建立最小资产库

- 房屋：3 种真正不同的轮廓，精修一栋近景主屋，再制作配套房屋。屋檐、瓦片、窗洞、窗台、门框、台阶及烟囱具有厚度和合理接缝。
- 植被：3 种不同枝干和树冠结构，1 种粉色树变体，以及草叶、花朵、矮灌木组合。树冠的外轮廓、多团块关系和大明暗面需要单独设计。
- 海岸：分层断面岩石和少量独立岩块；护栏模块增加接头、边缘与木材质感；灯塔按参考比例制作。
- 资产保留可编辑源文件，并导出适合浏览器加载的 GLB 与贴图。格式转换只负责交付，模型轮廓仍由美术验收决定。

通过条件：每类资产提供近景、侧面、背面截图，并在运行时中显示；没有悬浮、接缝穿透和异常法线。

### 3. 完整的材质制作

为沥青、墙石、屋顶瓦片、木材和岩石分别制作底色、表面法线、粗糙度、遮蔽贴图。纹理采用一致的实际尺寸，避免所有表面使用同一种颗粒尺度。

沥青体现细小骨料和低对比磨损；墙石有轻微色差、灰缝和边缘积尘；瓦片有层叠边缘和不规则色差；木纹沿构件方向延伸；岩石有面与裂隙之间的材质变化。颜色贴图避免烘入会与实时太阳重复的硬阴影。

通过条件：在相同中性灯光下，仅凭表面反光与细节即可区分木头、石头、瓦片和沥青；近景没有拉伸、明显接缝或高频闪烁。

### 4. 静态间接光照与动态阴影结合

静态村落与地面预计算间接光照，保留墙角、屋檐、树下和建筑之间的自然明暗。动态车辆继续使用实时阴影和与场景一致的天空/地面补光。环境遮蔽只补局部遮挡，不代替整个光照系统。

烘焙只包含选定的静态间接光照与遮挡分量，明确与实时阳光的分工，避免重复打光、重复阴影。为烘焙数据建立独立 UV、色彩空间和绑定流程；不能假设 GLB 自动携带并正确接入所有光照数据。

通过条件：阳光方向、阴影颜色和软硬边缘与参考一致；墙脚不悬浮，屋檐内部有层次；车辆经过日照与阴影区域时，没有明显“人物与环境属于两张图”的感觉。

### 5. 接入正式赛道并扩展

新增分区资产清单，记录资源路径、变换、材质绑定、光照数据和距离分级。加载成功后替换对应程序化场景分区，避免叠加两套房屋或地形。加载失败时可回退旧场景。

布局按近景、中景、远景规划，用有限但不同的房屋、植被组合形成自然节奏。保持道路、捷径及道具区域的空间约束。将散落在场景代码里的关键位置转为可编辑数据，便于后续修改地图。

### 6. 运行时验收

先测当前设备与浏览器的基线，再以桌面 1080p、60 FPS 为目标调整质量档；这是目标，不是已测得结果。记录实际帧耗时、卡顿峰值和资源用量。通过实例化、远近模型分级、分区加载与纹理压缩控制开销。

验收材料必须包含：

1. 相同画幅与固定镜头下的前/后对照图。
2. 屋檐、树根、路面与海岸各一张近景检查图。
3. 正式赛道至少一圈移动检查，验证阴影稳定性、贴图闪烁与模型切换。
4. 道路及捷径净空检查、场景切换资源释放检查。
5. 按构图、模型、材质、光照、运动稳定性、性能分别记录通过与剩余差距。测试通过不能代替画面验收。

## 第一阶段交付

一段接近参考图质量的实时美术样板、一组可编辑资产及贴图、固定镜头对照和移动检查结果。样板达到上述视觉标准之后，再复用资源扩展正式赛道。

## 技术依据

- Three.js MeshStandardMaterial 支持法线、粗糙度、环境遮蔽和光照贴图：<https://threejs.org/docs/pages/MeshStandardMaterial.html>
- Blender Cycles 可以将表面细节与静态光照烘焙为游戏使用的贴图：<https://docs.blender.org/manual/en/latest/render/cycles/baking.html>
- Three.js GLTFLoader 提供 GLB/glTF 资产及相关压缩资源的加载能力：<https://threejs.org/docs/pages/GLTFLoader.html>
