## 1. 产品目标与优化边界

### 1.1 核心体验

玩家应当能快速理解基本操作，通过练习明显提高圈速，并能解释自己为什么赢、为什么输。比赛中的关键决策包括入弯位置、漂移角度、出弯方向、氮气释放时机、超车路线和失误恢复。

第一主线是个人竞速。计时赛承担训练与低在线人数时的内容供给；道具赛和团队赛作为后续扩展。普通比赛允许免费进入，钱包连接不阻塞基础驾驶。

### 1.2 规则类别

| 标记 | 含义 | Codex 的处理方式 |
|---|---|---|
| 必须 | 正确性、公平性、数据一致性要求 | 满足规则；与既有约定冲突时记录并解决 |
| 默认 | 没有现成产品决策时的推荐行为 | 可据已有实现和用户约定调整，写明理由 |
| 调参 | 需要试玩和测量的初始数值 | 配置化，保留前后对比，不宣称已平衡 |
| 扩展 | 后续产品方向 | 不自动扩展当前交付范围 |

### 1.3 现有项目优先

- 保留现有引擎、语言、主要框架和运行方式。只有证据表明当前方案无法满足目标，才另行提出迁移方案。
- 不将项目强制改成浏览器游戏、手机游戏或某条特定公链；实际平台以仓库和既有要求为准。
- 不因本文偏重竞速而删除现有道具赛、地图、账号或资产功能。
- 使用原创角色、赛车、赛道、名称、界面和音效；参考机制后形成自己的内容。
- 不覆盖用户未提交的工作，不修改无关项目。对接口、存档、排行榜和已发行资产的兼容性作明确记录。
- P0/P1 是本次优化范围；P2 只保留规格和接口边界，除非用户另有授权。

## 4. 比赛规则与生命周期

### 4.1 默认比赛规格

| 配置 | 默认值 | 备注 |
|---|---:|---|
| 目标人数 | 8人 | 先验证4人，再扩至8人 |
| 普通赛道圈数 | 2圈 | 支持逐赛道配置 |
| 目标比赛时长 | 120—180秒 | 赛道设计目标，不强制减速或加速玩家 |
| 准备超时 | 30秒 | 未准备者退出该房间或取消本次开局 |
| 起跑倒计时 | 3秒 | 统一按服务器时间开始 |
| 首位完赛后窗口 | 20秒 | 最终截止取此时间与硬上限的较早者 |
| 比赛硬上限 | 300秒 | 到时剩余玩家标记DNF |
| 断线重连窗口 | 10秒 | 断线期间比赛计时继续 |
| 起步加速技巧 | 初版关闭 | 后续单独评估，不与出弯小喷混用 |

### 4.2 房间状态

`LOBBY → LOADING → COUNTDOWN → RACING → FINISH_WINDOW → FINALIZING → RESULTS → CLOSED`

`RACING` 达到硬上限或全员终止时，可以直接进入 `FINALIZING`。加载失败或开赛条件失效进入 `CANCELLED`，向参与者提供原因及返回入口。

必须实现以下约束：

- 倒计时结束前不能移动赛车或提前获得氮气；倒计时最后时刻取消也不能遗留可运行赛车。
- 开赛时锁定地图版本、模式、车辆性能、操控辅助类别和规则版本。
- 房主退出不得使其他玩家的权威比赛停止；当前为房主权威架构时，先明确其限制并按P1评估改造。
- 第一人合法冲线只开启一次完赛窗口，不重复缩短或延长截止时间。
- 全部玩家已完成、退出或失去资格时可以提前结算。
- 结算生成一次不可变比赛结果；展示重试和网络重发不产生第二份结果。
- 下一局创建新的 `raceId`，清理上一局氮气、道具、计时器、状态和临时事件监听。

### 4.3 排名与并列

完赛者按服务器确认的终点穿越时间排序。支持跨物理步的穿越时间插值，不能按客户端消息到达顺序排名。

比赛中的进度按“已完成圈数＋已通过的合法有向路段＋当前路段内进度”计算。分岔赛道使用连通的检查点/路段图，不能只比较世界坐标或距离终点的直线距离。

截止后，未完成者标记DNF；DNF显示顺序按合法进度，同进度按较早到达该进度排序。该显示顺序不等于完赛资格。

若完赛时间在权威时间分辨率内无法区分，允许并列。竞技积分采用并列占据名次的平均值；未来奖金赛事须按预先公布规则处理。UI可用稳定ID排序同名次展示，但不能用该排序决定胜负或钱款。

## 5. 驾驶与漂移实现要求

### 5.1 驾驶模型

采用现有引擎中的街机驾驶模型。车头方向和运动方向需要可分离，使侧滑可以持续、修正并收敛回抓地状态。物理更新使用固定步长；渲染、镜头和界面独立更新。若项目已有成熟步长和同步方案，先验证再调整。

普通转向、漂移、刹车和反打应该形成连续输入响应。低速转向要便于脱困，高速急转不能无代价完成。加速度、最高速度、侧向抓地、转向响应和漂移阻力分别配置，避免仅修改一个“速度倍率”控制所有手感。

保留已有输入习惯；没有既定键位时，使用WASD/方向键驾驶、Shift漂移、Ctrl氮气/道具、Q换位、R复位。支持按键重映射。已有自动油门可以保留，但小喷的触发动作和辅助类别必须单独定义并显示。

### 5.2 状态拆分

不要把所有组合塞进单个巨大状态枚举。建议按以下正交状态表达，名称仅表示逻辑职责，可映射到现有代码：

- 行驶：`GROUNDED / AIRBORNE / RESETTING / FINISHED`。
- 漂移：`GRIP / ENTERING / DRIFTING / RECOVERING`。
- 加速：`NONE / MINI_BOOST / NITRO`。
- 控制效果：是否受击、是否免疫、是否可与其他车碰撞。

复位和完赛会覆盖输入资格；氮气可以与漂移共存。落地、受击和重连必须通过明确的恢复逻辑，不能永久停在漂移或失控状态。

### 5.3 漂移条件与反馈

有效集气需要车辆着地、速度达标、存在真实侧滑、在合法赛道中向前行驶。按住漂移键但车辆没有侧滑时不集气。侧滑角度按地面切平面内的车头方向与实际速度方向计算，低速时避免对零向量求角度。

漂移要有入漂、维持、出漂三个过程。反打能修正方向，但不能瞬间消除所有侧滑并保留完整速度。长时间过大角度漂移需要额外速度损失；干净弧线应比乱甩方向获得更好的圈速。

显示轮胎痕迹、摩擦声、集气变化和出弯提示。普通HUD隐藏底层角度和系数；这些放入开发调试层。

### 5.5 参考集气公式

下式是方便复现和调优的起点，不要求替换已验证有效的模型：

```text
Vref = 该性能配置的普通最高速度，要求 > 0
v = 当前地面切平面内速度大小
a = 当前侧滑角度绝对值

angleWeight = 三角形权重：10°为0，30°为1，65°为0；区间外为0
speedWeight = clamp(v / Vref, 0, 1)
dForward = 在当前合法有向赛道路段上的正向进度增量
progressRatio = clamp(dForward / (Vref * dt), 0, 1)

若着地、未复位、v >= 0.35 * Vref、处于有效漂移且无严重碰撞：
    gain = 30 * dt * angleWeight * speedWeight * progressRatio
否则：
    gain = 0

energy = min(100, energy + gain)
若 energy == 100 且 storedNitro < 2：
    storedNitro += 1
    energy = 0
```

`dForward` 必须由连续合法路段求得，并按物理可达距离限幅；不能因切换投影到相邻发卡弯或复位瞬移获得巨大集气。以上各项共同决定获得速度，最终目标为普通有效弯约半瓶至一瓶，通过实测调整系数和赛道。

原地打转、倒车、卡墙、越界和复位不集气。合法向前的小幅补气动作可以保留，但需付出实际时间与速度成本。集气量本身不直接产生可兑现奖励。

## 6. 氮气、小喷及碰撞规则

### 6.1 氮气库存

最多储存2瓶，并允许额外保留最高100点未转换集气。满库存时新集气在100点封顶。释放一瓶后，满槽能量可以转换补入空位。因此“2瓶＋满槽”代表两瓶库存和一份待转换资源，HUD必须正确表现这个区别。

按键只有在获得服务器认可的激活时刻才消耗1瓶。正在使用的氮气不计入库存。相同输入序号、重复网络包和按住按键不能多次扣库存或多次启动。

氮气加速连续作用，不瞬移到最高速度；结束后平滑回落。连续氮气延长时间，不叠加速度上限。可在结束前150毫秒内缓存一次新按下事件，结束时检查库存与驾驶资格再启动。

复位取消当前加速并清空输入缓冲，保留已获得库存和集气；复位不补发资源。碰撞不暂停氮气计时。

### 6.2 小喷

一次合格漂移只产生一次小喷资格。有效漂移累计至少250毫秒，随后完成拉正，开启500毫秒触发窗口。手动油门模式使用新的油门按下事件；自动油门模式映射到明确的小喷动作，不能隐含触发无限加速。

一次资格被消费、超时、复位、严重撞击或完赛后立即失效。松开再按漂移键但没有新的有效漂移，不能重复获得资格。

初版同一时刻只使用一个加速档：氮气高于小喷，小喷高于普通。氮气期间小喷资格可以自然到期，但不叠加速度，也不在氮气结束后补发。后续若增加组合技巧，需同步修改规则版本和回归测试。

### 6.3 碰撞和复位

轻擦墙保留大部分切向速度，正面撞墙明显减速；优先使用现有碰撞法线与速度分解处理，不在已经产生物理损失后反复额外乘惩罚系数。车与车碰撞限制冲量，避免弹飞、穿透和持续压墙。

手动复位默认等待1.5秒，在最近的合法安全位置恢复；自动出界复位使用同一合法进度规则。等待期间计时继续。复位不能前移检查点或减少应走距离，复位后的朝向与赛道方向一致。

复位后1秒对其他车不可碰撞，仍与道路及墙体碰撞。持续停驶或逆行阻挡的车辆可幽灵化，但不能因此缩短路线。阈值按赛道、合法慢速弯和现有玩法调试，避免误伤正常玩家。

## 7. 赛道、训练与反馈

### 7.1 赛道数据

每条赛道记录：唯一ID、内容版本、圈数、起跑格、安全复位点、有向检查点、合法分支及合流点、路段进度、道路边界、危险区域、目标圈速和适用模式。

检查点覆盖完整可通行宽度，禁止通过跳台或分支绕过必经路段。发卡弯上下层、桥梁和相邻道路需要明确区分，避免仅按最近空间距离识别当前道路。

验收必须覆盖：正常路线、合法近路、逆向过点、跳过检查点、跨越终点侧面、掉落复位、桥下穿越、分支汇合。新赛道版本不能直接覆盖旧排行榜的可比条件。

### 7.2 内容规模

先在现有赛道优化；没有可用赛道时，创建一条灰盒测试赛道，包含直道、大弯、直角弯、发卡弯和连续S弯。灰盒优先用于验证驾驶，不能把它描述为已完成的正式美术地图。

完整内容目标为入门环道、技术街区和风险路线三种赛道职责。新增正式主题、场景资产和大量地图归入P2；P1可在测试场补齐必要结构。

### 7.3 计时和影子

计时记录至少绑定 `trackId + trackVersion + rulesVersion + performanceClass + assistClass`。平衡参数、地图、辅助类别变化后，建立新分组或新赛季，避免不可比成绩混在一个榜单。

影子不参与碰撞、不触发检查点和道具，不替代服务器上的玩家实体。可保存位置/朝向采样与时间戳作平滑播放；如果使用输入回放，必须验证引擎、物理版本和随机因素能支持所需一致性。

玩家可以挑战个人最佳与合法公共纪录。显示当前分段与最佳分段的差值。没有可靠参照时只显示实际碰撞次数和分段时间，不编造“损失多少秒”。

### 7.4 教学与HUD

最小教学依次验证：起步与转向、基础漂移、拉正与小喷、集满氮气并使用、合法完成一圈。教学可重试并显示当前动作反馈，不强制观看冗长说明。

比赛HUD包含名次、圈数、计时、氮气槽和库存、倒计时、小地图及必要的网络状态。未来道具模式增加两个道具位和攻击预警。结算显示名次、DNF状态、最佳圈、分段和再来一局。

竞赛成绩与奖励审核分开显示：“比赛已结束”可以立即出现，“奖励待审核”必须与“已到账”区分。链上提交成功与交易最终确认也应区分。

镜头保持前方道路可见，提供震动和速度效果强度开关。辅助设置保存到账号或本地用户配置；影响成绩的辅助类别随开赛快照锁定。

## 8. 联机与权威判定

### 8.1 权责

客户端负责输入采集、即时表现、镜头、音效和界面。服务器负责有效输入、赛车权威运动状态、碰撞结果、库存、检查点、圈数、道具、截止时间和最终排名。

如果现有项目由客户端直接上传位置、圈数或成绩并被无条件接受，记录为权威判定缺口。浏览器签名或钱包签名只能说明消息来源，不能证明消息中的速度和成绩真实。

采用现有协议与框架，先建立服务器可验证的最小赛车模拟。客户端可以预测自己的运动，收到权威快照后依据已确认输入序号校正；其他车辆通过插值呈现。不能直接依赖客户端申报的集气、氮气次数或完赛事件。

### 8.2 消息语义

以下是逻辑字段，不要求另建指定语言的类或替换既有协议。可以增加字段，但不能丢失关键身份、版本和去重语义。

| 消息 | 关键字段 | 约束 |
|---|---|---|
| InputFrame | raceId、sessionId、sequence、clientTick、油门/刹车/方向、动作边沿事件 | 玩家身份取自认证会话；序号去重；限制频率及可接受时间窗口 |
| StateSnapshot | raceId、serverTick、rulesVersion、玩家位置/速度/朝向、资源、圈数、状态、已确认输入序号 | 客户端以权威状态校正；拒绝旧比赛和倒序快照 |
| RaceEvent | raceId、eventId、serverTick、事件类型、权威事件负载 | 音效、动画和提示按eventId去重 |
| RaceResult | raceId、地图/规则/性能/辅助版本、完赛时间、名次、状态、结果摘要 | 每局冻结一次，不能被重连或刷新重写 |

连接会话与钱包身份分开处理。令牌和服务端密钥不写入前端包、公开日志或回放。输入方向、浮点值、时间戳和序号都需范围检查，包括NaN/Infinity等无效值。

### 8.3 时序与恢复

- 原型起点：权威物理60Hz，快照20Hz；已有同步策略先测量。频率一致性、带宽和服务器成本一起评估。
- 计时以服务器单调时钟/比赛tick为依据，不使用客户端可修改的系统时间。
- 断线期间车辆按服务器控制进入安全滑行或刹停，随后按规则幽灵化；不默认由AI替玩家完成奖励比赛。
- 10秒内重连恢复同一个玩家与比赛，返回完整权威快照及已确认输入序号，不重置位置、资源或计时。
- 超过窗口记为退出/DNF，停止参与该局；比赛继续。旁观/退出操作不能变相延长重连窗口。
- 切后台或低帧率不能暂停服务器比赛。恢复时丢弃过期积压输入，不用巨大的单帧dt补算几秒物理。
- 严重丢包时提供明确状态；不通过无限回滚改变已经冻结的比赛结果。

### 8.4 联机验证边界

至少覆盖0、80、150毫秒模拟往返延迟，并在150毫秒下附加2%丢包验证。记录带宽、纠正幅度、重复事件、状态发散和重连结果。目标是在测试条件下不出现永久状态分歧、重复使用资源或不同最终排名；驾驶舒适度另行试玩评估。

四个独立客户端连接同一服务，可证明基础联机；八个自动化客户端可以证明限定场景下的负载和协议一致性。这两者均不能代替真实异地玩家体验测试，报告必须区分。

## 9. 数据、配置和模块边界

### 9.1 逻辑模块

| 职责 | 接收 | 产出 |
|---|---|---|
| 输入适配 | 键盘/手柄/触摸输入 | 归一化驾驶值和带序号的动作事件 |
| 车辆模拟 | 有效输入、固定dt、性能配置、道路信息 | 位置、速度、朝向及地面/碰撞状态 |
| 漂移与资源 | 车辆状态、赛道进度、漂移动作 | 漂移状态、能量、库存、加速事件 |
| 赛道进度 | 权威运动轨迹、检查点图 | 合法进度、圈数、复位位置 |
| 比赛控制 | 房间状态、玩家状态、服务器时间 | 开赛、截止、结果和取消事件 |
| 网络同步 | 已认证输入、权威状态 | 去重后的输入流、快照、事件 |
| 成绩与回放 | 冻结结果、关键采样 | 可追溯成绩、榜单、影子文件 |
| 奖励适配 | 已审核资格、冻结预算、结果ID | 可领取记录及幂等领取状态 |

这些是职责边界，不要求把每一行新建成一个服务。沿用现有目录和依赖方向，避免为了套架构而大规模拆仓库。

### 9.2 持久化记录

比赛记录绑定地图、规则、性能配置和操控辅助版本，保存开始/结束时间、参赛名单、结果、异常标记及回放索引。单个玩家的比赛记录至少包含合法完赛时间或DNF原因。

推荐唯一约束：比赛结果按 `raceId` 唯一；玩家结果按 `raceId + playerId` 唯一；奖励资格按 `eventId + raceId + playerId + rewardType` 唯一。实际数据库字段可以不同，但必须保证相同语义。

### 9.3 参数版本与兼容

数值集中到现有配置系统，按模式、性能类别及赛道覆写。禁止客户端和服务器各藏一份不同常量。开赛锁定参数快照；比赛中途热更新只影响新房间。

改动影响圈速的参数时增加 `rulesVersion` 或等效版本。保存旧成绩和回放的版本信息；不承诺不同物理版本输入回放逐帧一致。存档或数据库变更使用项目既有迁移方式，先在测试副本验证并写明回滚策略。

## 10. 链游接入与奖励边界

### 10.1 链上与链下

实时驾驶、道具和比赛判定在游戏服务中进行。链上可记录外观资产所有权、已落实的赛事预算和奖励领取。完整轨迹可以存储在链下，只对必要摘要上链。

哈希摘要能帮助检查记录是否被更改，但不能自行证明比赛公正。服务器签名的结果仍依赖服务器真实性、审查和权限控制，不得宣传为合约已经验证全部驾驶过程。

普通游戏不需要每局签钱包。绑定钱包使用带随机挑战值、有效期和应用域的所有权验证，挑战值只能使用一次。奖励地址在资格冻结时固定；改绑默认影响未来资格，历史奖励改址通过单独审查处理。

可交易外观不提高竞赛车速、集气率、道具位或奖金倍率。外观所有权在开赛前验证并锁定当局展示；开赛后的资产转移影响下一局。更复杂的参赛通行证/质押资产不在本次默认范围内。

### 10.2 奖励状态

`PENDING_REVIEW → APPROVED → CLAIMABLE → CLAIMED`

未通过检查的资格进入 `REJECTED`，不能仅通过刷新或重新签名恢复为可领取。普通成绩展示和奖励状态分别保存。资金尚未落实时，不能将资格标记为有资金保障的 `CLAIMABLE`。

领奖幂等同时覆盖数据库、消息队列和合约：任务重试、页面刷新、交易重发及同一结果从两个会话提交都不能重复分配或领取。

### 10.3 现有合约/奖金功能的检查项

签名或领取证明需要绑定应用域、chainId、验证合约、赛事ID、比赛ID、收款地址、奖励资产、最小单位整数金额、唯一领取标识和有效期；实际形式可为签名或批量Merkle领取，但作用域及去重约束必须等价。

必须检查错误链、错误合约、改收款人、改金额、过期、已领取及跨赛事复用。链上金额采用最小单位整数，禁止用浮点数累计资金。交易提交、回执成功和满足确认策略分别记录；链重组或失败交易不能永久错误标记已到账。

项目运营者控制签名/审核时，记录其权限、密钥轮换和异常暂停范围。不要要求用户提供私钥，也不要为了读取链上数据扫描无关本地凭据。

没有真实合约环境时，可以完成接口、模拟领取和本地测试，但必须标记“模拟资产/模拟结算”。未经用户授权不部署正式合约或转移真实资产。

### 10.4 经济约束

普通比赛奖励经验、不可交易金币或通行证进度。可兑现实物/代币的赛事奖励来自事先确定且已落实的预算，总分配额不得超过可用预算扣除已承诺额度。

不按在线时长、漂移次数、集气量或钱包数量无限产生可兑现奖励。不把“连接一个钱包”当作证明只有一名真实玩家。异常账户关联、反复互送胜利和重复参赛关系是审查信号，需要证据，不直接等同作弊结论。

不在本次优化中自动新增发币、NFT发行、质押、繁殖、租赁、燃料收费或付费奖金门票。已有产品规则若与本节冲突，先记录实际机制和影响，涉及财产权益的变化交由用户决定。

## 11. 道具与团队扩展规格（P2）

本节使后续开发保持兼容。当前已有相关玩法时，用本节检查逻辑缺陷；尚未实现时，只记录后续任务，不自动扩大本轮交付。

### 11.1 道具模式

保留驾驶、漂移和小喷。默认关闭漂移生成氮气瓶，主要加速资源来自道具箱。两个道具位，免费换位，满位不拾取、不自动覆盖。攻击、随机结果和命中均由服务器决定。

| 道具 | 原型效果 | 反制/边界 |
|---|---|---|
| 追踪弹 | 锁定前方目标，命中后短暂减速 | 锁定预警、护盾；目标已完赛则取消有效攻击 |
| 能量护盾 | 最多2秒内抵挡一次攻击 | 抵挡后立即消耗，不累积无限层数 |
| 地面陷阱 | 可见的局部减速区，作用约1.5秒 | 可绕行；控制地面数量和存在时长 |
| 范围脉冲 | 可见预警1秒后产生区域效果 | 可提前驶离；不越过未声明的道路层级命中 |
| 追赶磁力 | 朝前方目标加速接近，最多1.5秒 | 只加速自己，目标丢失或超越后停止 |
| 加速包 | 约2秒加速 | 使用统一加速优先规则，碰撞照常损速 |

单次硬控制原型上限1秒，恢复后1秒硬控制免疫；减速有下限、总效果有优先级，禁止连续效果导致永久失控。初期团队模式关闭队友伤害，投射物不锁定队友。

道具带按单车、单圈、带ID限制一次拾取；不能倒车反复刷同一带。箱子在客户端的动画不是发放凭据，服务器确认穿越后才发放。

下表为8人原型权重，行内合计100，需试玩调优：

| 位置组 | 追踪弹 | 护盾 | 陷阱 | 脉冲 | 磁力 | 加速包 |
|---|---:|---:|---:|---:|---:|---:|
| 前排 | 15 | 45 | 25 | 10 | 0 | 5 |
| 中排 | 25 | 20 | 15 | 20 | 10 | 10 |
| 后排 | 20 | 10 | 5 | 15 | 25 | 25 |

默认前排为第1—2、中排第3—5、后排第6—8；小人数使用归一化排名分组。为减少瞬间故意掉位刷取，以最近5秒平均合法排名确定分组，开局不足5秒时使用已有历史。更复杂的领先距离修正另行配置和测试，不能偷偷提高基础车速。

随机种子由服务器安全生成并在审查材料中保存，不在比赛前发给客户端预测未来道具。赛后公开种子或承诺值不自动证明运营者从未操纵随机，产品说明需与实际验证能力一致。

### 11.2 团队模式

团体竞速默认4对4，合法完赛名次积分为10、8、6、5、4、3、2、1，DNF为0。全队相加，高分获胜；平分比较双方最佳合法完赛名次，全员DNF判平局。完全同时且无法区分时按并列规则处理。

团体道具默认本队任一成员率先合法冲线即获胜。队伍在开局锁定，不能中途换队。名次、队伍结果和个人展示分别记录，避免只更新第一名而遗漏队伍成员。

初版不新增团队氮气、英雄技能或付费战斗能力。后续扩展必须单独说明资源来源、叠加规则和反制方式。

## 12. 性能、调试与运行可观测性

### 12.1 性能目标与测量方法

先记录当前最低支持设备、分辨率、画质、浏览器/客户端版本、引擎版本和服务器规格。无法获得真实目标设备时，在当前环境测试并说明限制，不编造“低配流畅”。

桌面原型参考目标为正常8车比赛60fps，稳态帧耗时P95不高于20毫秒、P99不高于33毫秒。这些是待验证目标，不能据此声称已满足所有设备。物理60Hz时服务器单步处理P95需要低于16.7毫秒，并为其他任务保留余量。

先预热场景，再测量固定赛道和固定负载。对比同一设备、分辨率、画质、路线和参数版本的前后结果。记录平均值、P95/P99和最差卡顿事件，避免只看瞬时FPS。

检查对象生成/销毁、轮胎痕迹、粒子、音效实例、纹理、碰撞体、网络序列化和监听器积累。按性能分析结果优化，不能无证据地改写整套渲染或物理系统。

连续完成10局并重复进出房间，确认不会每局新增残留车辆、计时器、网络订阅或音频实例。内存允许资源缓存带来的平台期，但不能随局数持续无界增长。

### 12.2 调试信息

仅在开发模式显示：权威tick、输入序号、车辆速度、侧滑角、当前路段、有效前进量、集气增量、氮气库存、加速状态、网络RTT及校正距离。

结构化日志使用 `raceId`、玩家内部ID、`eventId` 和规则版本关联。记录开赛、复位、异常输入、库存变动、检查点、完赛、结果冻结及奖励状态变化。避免默认逐帧写入大量生产日志；诊断采样可单独开启。

回放保存策略按隐私和成本确定，并在项目报告中写明。面向用户的错误提示提供下一步操作，底层堆栈和密钥不显示给普通玩家。

## 13. Codex 分阶段执行任务

以下任务顺序体现依赖。现有奖励系统存在资金安全缺陷时，将M08相关止损修复提前到M01之后，在本地完成验证；任何生产暂停或资产操作按用户授权范围处理。

每个任务开始前，将逻辑模块映射到真实文件及实际验证命令。每个任务结束后更新状态为“完成 / 部分完成 / 阻塞 / 不适用”，并附证据。不使用虚构路径或仅写“测试通过”。

### M01｜建立运行基线与问题清单｜P0

- 输入：现有仓库、开发规则和可用运行环境。
- 动作：读取结构和版本控制状态；启动当前项目；完成一次现有流程；运行已有相关测试；复现主要问题。
- 输出：PROJECT_AUDIT、映射到真实文件的IMPLEMENTATION_PLAN，以及带环境信息的基线记录。
- 验收：别人可按记录重现现有启动方式和至少一个真实问题；没有问题的模块可以标记正常，不能为凑数编造缺陷。

### M02｜修复比赛生命周期和合法进度｜P0，依赖M01

- 输入：现有房间、赛道、圈数、计时和复位逻辑。
- 动作：统一开赛/截止/结算状态；修复检查点顺序、终点穿越与复位进度；保证结果只冻结一次。
- 输出：可以反复完成的比赛闭环和对应回归用例。
- 验收：正常完赛、提前退出、硬上限、DNF、复位、重复结算和下一局清理均符合第4/6/7节。

### M03｜优化固定步长驾驶和漂移｜P0，依赖M01/M02

- 输入：现有车辆控制器、道路碰撞、输入及物理配置。
- 动作：确认单位和固定步长；将车头/运动方向及抓地/侧滑关系处理清楚；修复入漂、维持、反打与出漂；用测试场验证。
- 输出：稳定可控的驾驶实现、配置快照与前后对比。
- 验收：不同渲染帧率不改变基本物理结果；车能通过测试场各类弯道；不会永久侧滑、瞬间转向保全速或轻触墙后弹飞。

### M04｜统一集气、氮气和小喷｜P0，依赖M03

- 输入：权威或本地车辆状态、合法进度、输入边沿、资源配置。
- 动作：实现或修复第5/6节资源语义；配置化系数；去重输入；覆盖满库存、满槽、缓冲、复位和重连边界。
- 输出：可验证的资源状态转换、HUD实际值与关键回归用例。
- 验收：原地和卡墙不集气；一个动作不会重复触发；库存与加速不因帧率、网络重发或复位增殖；同局客户端和服务器资源一致。

### M05｜修复或补齐最小权威联机｜已有系统关键缺陷P0，新增/体验P1，依赖M02—M04

- 输入：现有服务器/协议；没有服务时根据现有技术栈建立最小比赛进程，并记录运行方式。
- 动作：认证输入、限制时序、权威模拟与结果；同步状态；补齐重连与完整快照；按风险加入本地预测/远端插值。
- 输出：至少4个独立客户端可加入同一比赛；目标8客户端的限定负载记录；延迟与丢包验证。
- 验收：每个客户端显示相同最终结果；不能用伪造位置或圈数赢比赛；断线不暂停比赛、不补资源；测试范围与真实互联网验证明确区分。

### M06｜改进HUD、教学、计时和影子｜P1，依赖M02—M04

- 输入：已稳定的驾驶状态、比赛事件与历史成绩存储。
- 动作：显示真实资源和状态；补齐最小教学；记录分段成绩；保存并播放不参与物理的影子；提供再来一局。
- 输出：新玩家可完成教学，玩家可挑战可比条件下的个人最佳。
- 验收：UI与实际状态一致；影子不会触发比赛逻辑；规则/地图/辅助版本不同的成绩不会混榜；没有依据的损失估算不显示。

### M07｜性能与资源释放｜P1，依赖对应可运行模块

- 输入：固定设备/场景的性能基线，已有性能分析工具。
- 动作：定位最大实际瓶颈；优化必要的对象、渲染、物理或消息处理；验证连续比赛的释放行为。
- 输出：同条件前后帧耗时、内存与网络记录；重要瓶颈原因及修改。
- 验收：目标设备与测试范围明确；关键瓶颈有可测改善，功能无回归；连续10局没有明显累积残留。

### M08｜核查已有资产和奖励结算｜存在系统时P0/P1，不存在时不适用

- 输入：现有账号、钱包、数据库、奖励接口、合约及可用测试环境。
- 动作：验证结果资格、预算、签名作用域、幂等和确认状态；修复相关缺陷；保留既有资产权益和数据兼容。
- 输出：真实环境范围说明、本地/测试环境验证及修复结果。
- 验收：同一资格不能重复分配和领取；伪造参数/过期/跨链请求被拒绝；并发分配不超过预算；链上未确认时不显示已到账。

### M09｜最终回归与交接｜P1，依赖本次适用任务

- 输入：全部任务状态、参数版本和改动清单。
- 动作：运行必要的构建和核心回归；从首次进入到比赛结束走通用户流程；检查未提交改动；记录尚未完成的依赖。
- 输出：VALIDATION_REPORT、TUNING_LOG、启动/测试方式、修改说明和后续P2清单。
- 验收：可启动成果与报告一致；无测试证据的项目标记未验证；不把文档完成等同于产品完成。

## 14. 验收矩阵

高影响的状态、竞赛结果和奖励逻辑需要自动化或可重复脚本验证；驾驶手感使用固定路线、记录和人工试玩。低影响的文案/样式修正只做适当检查，不要求为了覆盖率编写镜像实现的测试。

表中“测试”表示可重复的用例要求。Codex应结合仓库真实测试框架实现关键项，并记录执行命令、结果和证据路径；未实现的P2和不存在的奖励系统标记不适用。

| ID | 场景/输入 | 预期结果 |
|---|---|---|
| AC01 | 正常加入、准备、倒计时、完成两圈 | 仅倒计时结束可移动，合法完赛并显示结果 |
| AC02 | 同一输入记录，以30/60/120fps渲染，固定物理步长运行 | 圈数、库存、事件次数一致；位置和时间在项目预定数值容差内 |
| AC03 | 低速按住漂移、静止转向、原地打转 | 不产生有效集气 |
| AC04 | 固定路线中完成合格漂移并拉正 | 获得一次小喷资格，在窗口内新按油门只触发一次 |
| AC05 | 持续按住油门/漂移，重复同一输入序号 | 不重复小喷、不生成多份同一动作 |
| AC06 | 2瓶库存、100点能量，启动1瓶 | 启动消耗1瓶，满槽补回1瓶并清零能量；总资源不凭空增加 |
| AC07 | 连续氮气与小喷同时可用 | 遵循加速优先级，速度倍率不累乘 |
| AC08 | 氮气结束前150毫秒输入下一瓶；重复发送该输入 | 最多缓存并启动一次；无库存不启动 |
| AC09 | 使用氮气期间正面撞墙 | 正常损速，氮气计时不中断或延长 |
| AC10 | 持续卡墙、倒车、越界、复位瞬移 | 不因异常进度获得集气或新检查点 |
| AC11 | 跳过必经检查点后穿过终点 | 不完成有效圈数；提示或记录缺失进度 |
| AC12 | 走合法分支并从合流点返回 | 合法进度连续，正常完成圈数 |
| AC13 | 发卡弯近邻道路、桥下穿越 | 不投影到错误路段、不跳进度 |
| AC14 | 在终点前后、跳台和近路入口手动复位 | 不获得更靠前的合法进度；等待时间计入比赛 |
| AC15 | 重复发送首位完赛事件 | 完赛窗口只启动一次 |
| AC16 | 第一人于295秒完赛 | 其他人截止时间仍为300秒硬上限 |
| AC17 | 所有人DNF或退出 | 正确结束，显示原因，不无限等待 |
| AC18 | 同tick近乎同时冲线 | 使用穿越时间判定；无法区分时并列，不按消息先后排名 |
| AC19 | 断线5秒后重连 | 同一玩家继续原比赛；计时继续；位置/库存来自权威快照 |
| AC20 | 断线超过10秒、反复更换会话 | 原比赛身份不重复创建；不能反复延长重连窗口 |
| AC21 | 提交超频、倒序、NaN、伪造位置/圈数数据 | 无效输入被拒绝或忽略，服务不中断，结果不被篡改 |
| AC22 | 4客户端同场完整比赛；8客户端限定负载 | 所有客户端最终结果相同；记录真实客户端类型与负载 |
| AC23 | RTT150毫秒＋2%丢包，含漂移/氮气/重连 | 无永久资源分歧、重复事件和不同最终排名 |
| AC24 | 切后台3秒后恢复 | 比赛未暂停，不用积压输入瞬移或补发动作 |
| AC25 | 保存/播放个人最佳影子 | 影子位置按记录播放，但不碰撞、不拾取、不计圈 |
| AC26 | 更新地图、性能或辅助类别 | 新成绩进入正确分组，旧成绩及版本保留 |
| AC27 | 连续10局并重复进出房间 | 无上一局资源残留，无监听/实体/计时器持续累积 |
| AC28 | HUD显示集气满槽、氮气使用、DNF和待审核 | 显示与实际状态一致，待审核不显示为已到账 |
| AC29 | 同一奖励资格并发提交两次 | 数据库仅分配一次；合约仅允许领取一次 |
| AC30 | 1000最小单位预算，两个600单位请求并发分配 | 至多一个获得完整600额度；不能合计承诺1200 |
| AC31 | 修改领取地址/金额、错误链/合约、过期证明、跨赛事重放 | 全部拒绝，正常请求仍可按规则处理 |
| AC32 | 交易已提交但失败或确认被重组影响 | 不永久标记已到账，按确认策略恢复/重试 |
| AC33 | 正常账号首次进入，未连接钱包 | 可完成基础教学和普通比赛 |
| AC34 | 道具满位、倒车再次穿越同一道具带 | 不覆盖库存、不重复领取该圈该道具带的资源 |
| AC35 | 连续道具命中、护盾、免疫同时发生 | 一次性消耗正确，不重复硬控或永久失控 |
| AC36 | 4对4含DNF、平分、同时冲线 | 团体积分与胜负遵循第11节，所有成员获得一致队伍结果 |

AC34—AC36仅在已有或已明确授权实现对应P2模式时执行。AC29—AC32仅适用于已有或另行授权的奖励系统，不能为完成验收表而自动发行资产或开启奖金功能。

AC02的数值容差由Codex在读取当前引擎与基线后先写入计划，再测试；不得看到失败后无依据扩大容差。非确定性物理引擎不能用“不逐帧相同”直接认定失败，但应验证结果语义与误差边界。

## 15. 驾驶手感与留存假设的试玩验证

功能正确不等于好玩。先固定一条测试路线和性能配置，关闭钱包与兑现奖励提示，邀请具备不同赛车经验的测试者试玩。没有真实测试者时，Codex只能提供功能验证和待验证假设，不能虚构玩家反馈。

建议每位测试者先完成教学，再进行10次同赛道尝试。记录完成率、圈速中位数、碰撞次数、有效漂移比例、氮气获得/使用次数、满槽浪费时间和主动再开一局的意愿。

判断方向：练习是否使多数人的圈速和碰撞表现改善；合理路线是否优于无意义长漂；氮气是否有多种合理释放位置；失误后是否仍能继续比赛；玩家能否说清某次超车或失败的原因。

不同技能水平要分别观察，不能只用熟练开发者的圈速决定门槛。小样本可以指导调参，不能据此宣称已验证市场留存、经济可持续性或大规模竞技公平。

每次调参尽量只改变一个相关参数组，记录配置版本、原因、测试条件、观察结果及保留/回退决定。依赖同一效果的参数必须一起修改时，说明耦合关系。

## 16. 交付要求与停止条件

### 16.1 Codex 最终交付

1. 可以运行的项目及实际启动方式，说明当前平台和所需环境。
2. 真实问题清单与修复结果，按“问题—原因—修改—证据”记录。
3. 修改文件清单及每项修改的用途，说明兼容性和存档影响。
4. 实际构建/测试命令、执行结果、联机测试人数与模拟网络条件。
5. 参数版本及调优记录，不只写“手感优化完成”。
6. 适用验收项的通过/失败/未验证/不适用状态。
7. 剩余问题与外部依赖，并给出可以继续推进的具体下一步。

### 16.2 允许结束本轮实现的条件

本次适用的P0和P1任务完成且获得必要验证，或剩余工作确实因访问权限、外部环境、用户待决的关键规则而阻塞。阻塞时先完成其他独立任务，再集中报告，不反复询问普通实现细节。

不要把尚未授权的P2全部实现作为结束条件，也不要以“计划已生成”“界面已美化”替代核心比赛闭环。构建失败、关键测试失败或奖励重复领取等问题不能标记为整体完成。
